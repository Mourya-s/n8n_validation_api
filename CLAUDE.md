# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

All commands run from the `comparison-service/` directory.

```bash
# Install dependencies
pip install -r requirements.txt

# Run the API locally (reload driven by RELOAD env var, default off)
uvicorn app:app --reload

# Run the full test suite
pytest

# Run a single test
pytest test_api.py::test_row_count_mismatch_detected

# Run the catalog-to-catalog validator from the CLI (no HTTP server needed)
python app.py validate-catalogs --source-catalog A --target-catalog B \
    [--schemas s1,s2] [--tables t1,t2] [--no-column-order] \
    [--mode COUNT_ONLY|STATISTICS|HASH|FULL] [--csv out.csv] [--excel out.xlsx] \
    [--primary-keys 'schema.table=col1,col2;other_table=col']

# Run the Azure Blob CSV -> single Databricks table validator from the CLI
python app.py validate-csv --source-blob path/file.csv \
    --target-catalog A --target-schema B --target-table C [--primary-key id] \
    [--no-column-order] [--mode COUNT_ONLY|STATISTICS|HASH|FULL] \
    [--csv out.csv] [--excel out.xlsx] [--azure-env .env.azure]

# Run the Azure SQL Database -> Databricks catalog validator from the CLI
python app.py validate-sql --target-catalog A \
    [--schemas s1,s2] [--tables t1,t2] [--schema-map 'dbo=target_schema'] \
    [--no-column-order] [--mode COUNT_ONLY|STATISTICS|HASH|FULL] \
    [--primary-keys 'schema.table=col1,col2;other_table=col'] \
    [--csv out.csv] [--excel out.xlsx] [--azure-sql-env .env.azuresql]
```

There is no lint/format tooling configured in this repo (no ruff/black/flake8 config present).

Config is via `.env` files (loaded by `python-dotenv`) or real environment variables. `DATABRICKS_HOST`/`DATABRICKS_TOKEN`/`DATABRICKS_HTTP_PATH` are always read from `.env` (or the environment) by all three CLI subcommands and the FastAPI app. Each other data source has its own **separate** env file so credential sets can be rotated independently: `validate-catalogs`/`POST /compare` read `AZURE_STORAGE_ACCOUNT`/`AZURE_STORAGE_KEY`/`AZURE_CONTAINER` from `.env`/the environment (`AZURE_STORAGE_ACCOUNT`/`AZURE_CONTAINER` default to `n8nstorages`/`n8ncontainer` if unset); `validate-csv` loads Azure Blob Storage credentials from `.env.azure` (path overridable via `--azure-env`); `validate-sql` loads Azure SQL Database credentials (`AZURE_SQL_SERVER`/`AZURE_SQL_DATABASE`/`AZURE_SQL_USERNAME`/`AZURE_SQL_PASSWORD`) from `.env.azuresql` (path overridable via `--azure-sql-env`).

## Architecture

FastAPI POC service, designed to be called from **n8n workflows**, that validates data migrations in two independent modes. `app.py` is the only entrypoint (HTTP via uvicorn, or CLI via `python app.py validate-catalogs ...`); it wires connectors → engine/validator via FastAPI `Depends`, and does no comparison logic itself.

**Strict layering, enforced across all files**: connectors do I/O only and never decide pass/fail; the engine/validator classes contain all comparison/decision logic and never talk to a data source directly; `report_generator.py` only knows how to render an already-built result object to CSV/Excel.

### Four independent comparison paths (do not conflate them)

1. **Row-level CSV-vs-Databricks comparison** (`ComparisonEngine` in `comparison_engine.py`, `POST /compare`) — original/legacy path. Loads a full CSV from Azure Blob Storage (`AzureConnector.read_csv`) and a full Databricks table into pandas, then compares schema, duplicates, missing/extra rows, nulls, and dtypes in-memory. `ComparisonRequest`/`ComparisonResponse` in `models.py` (aliased from `CompareRequest`/`ComparisonResult` for backward compatibility). Note `_compare_values` is currently a stub that always reports zero mismatches.

2. **Databricks catalog-to-catalog validation** (`CatalogValidator` in `comparison_engine.py`, `POST /validate-catalogs` and `POST /validate-catalogs/report`) — the actively-developed path. Recursively walks catalog → schemas → tables → columns → data as a fixed ~15-stage sequence (see numbered stage comments in `comparison_engine.py` and `_validate_table`). Every check is pushed down as SQL via `DatabricksConnector` (`SHOW CATALOGS`/`SHOW SCHEMAS`/`information_schema.columns`, aggregate `SUM`/`COUNT DISTINCT`/`MIN`/`MAX` in one query per table, key-based `EXCEPT`/hash-join row diffs) — **no full table is ever loaded into pandas or collected**, since catalogs can be arbitrarily large. Status aggregation is never hardcoded per-stage; it always flows bottom-up through `CatalogValidator.calculate_overall_status` (ERROR > FAIL > SKIPPED > PASS precedence).

   - `DataCompareMode` (`COUNT_ONLY` / `STATISTICS` / `HASH` / `FULL`) controls how expensive stage 15 (actual row-level data diff) is. Default is `STATISTICS`, which relies on the row count/null/distinct/min-max checks already done above and explicitly skips row-level diffing. `HASH`/`FULL` require a configured primary/business key per table (`request.primary_keys`, keyed by `"schema.table"` or bare table name) or that table's data stage is safely skipped rather than erroring. The CLI's `--primary-keys 'schema.table=col1,col2;other_table=col'` flag builds this map; the HTTP API takes it directly as JSON.
   - Only in `FULL` mode, `DatabricksConnector.key_based_row_diff` additionally calls `_changed_row_detail`, which re-fetches the full key+value columns (plus a whole-row `hash()`) for the sampled changed keys from both sides, diffs them column-by-column in Python, and returns one entry per row with its mismatched column names, before/after values, and both row hashes. This becomes `DataValidationResult.sample_changed_detail: List[RowMismatchDetail]` (`models.py`) — the source for the Excel "Data Mismatches" sheet. `HASH` mode still only returns counts (no detail fetch) since it's meant to be cheaper than `FULL`.
   - `CatalogValidator._EXCLUDED_SCHEMAS` (currently `{"information_schema"}`) is filtered out in `compare_schemas` before common/missing/extra are computed, so Databricks' built-in system schema is never validated and never reported as a false missing/extra schema difference.
   - `ValidationStatus` (PASS/FAIL/ERROR/SKIPPED) is intentionally a different enum from `ComparisonStatus` (PASS/WARN/FAIL) used by the row-level path — ERROR (technical failure, e.g. permission denied) is kept distinct from FAIL (real validation mismatch) so one bad table doesn't get conflated with a genuine data difference, and doesn't abort validation of the rest of the catalog.
   - **Row-hash comparison stage** (`CatalogValidator._run_row_hash_stage`/`compare_row_hashes`, `DatabricksConnector.get_row_hashes`) — a separate, cheaper mechanism from `key_based_row_diff` above, and the *primary* way row-level mismatches get detected: it runs whenever a primary key is configured for a table, **independent of `data_compare_mode`** (so it fires even under the default `STATISTICS` mode, unlike `compare_data`'s HASH/FULL-gated diff). `get_row_hashes` issues one pushed-down query per side — `SELECT <pk_cols>, sha2(concat_ws('||', COALESCE(CAST(col AS STRING), '\x01NULL\x01'), ...), 256) AS row_hash FROM ...` over a fixed, alphabetically-sorted business-column list (PK excluded) so both sides hash identically; the `\x01NULL\x01` sentinel keeps real NULLs from colliding with an empty-string value. `compare_row_hashes` (pure logic, no I/O) joins both hash sets **by primary key, never row position**, and classifies every key as `MISMATCH` (hash differs), `MISSING_IN_TARGET`, or `MISSING_IN_SOURCE`, plus a `mismatch_percentage` over the union of keys seen on either side. Results land on the same `DataValidationResult` as `compare_data` (`row_hash_mismatches: List[RowHashMismatch]`, `row_hash_mismatch_count`, `row_hash_mismatch_percentage` in `models.py`) — if `compare_data` itself was SKIPPED (e.g. STATISTICS mode), this stage still overrides that table's `data.status` to PASS/FAIL based on its own findings.
   - **No-primary-key fallback**: if a table has no entry in `request.primary_keys`, `CatalogValidator._run_row_hash_stage_by_row_number`/`DatabricksConnector.get_row_hashes_by_row_number` (and the equivalent methods in `azure_sql_connector.py`/`azure_row_validator.py` for the other two paths below) substitute a synthetic key: `ROW_NUMBER() OVER (ORDER BY <every common column>)` computed independently on each side. This is a best-effort fallback, not a real key — sorting by every column means two logically-identical rows always land on the same row number regardless of physical storage order, but it can only meaningfully compare two tables whose row **sets** are otherwise identical, and it cannot pinpoint which specific record changed (`DataValidationResult.note` explains this in the result whenever the fallback fires). `key_columns` becomes `["row_number"]` in this case.
   - `report_generator.py` has two output paths sharing the same row-builders: `generate_csv_report` writes a flat "Table Validation"-shaped `.csv`; `generate_excel_report` writes a 6-sheet `.xlsx` — **Summary** (overall status, timestamp/duration, total/passed/failed/error/skipped table counts, pass %), **Table Validation** (one row per table: Source/Target Schema+Table, Overall Status, Schema Match, Column Order, row counts, per-check statuses, Mismatch Count/%, Row Hash Mismatch Count/%, Validation Timestamp, Duration — sorted by schema, then FAIL/ERROR-before-PASS/SKIPPED, then table, and grouped into a collapsible Excel outline per schema), **Column Validation** (one row per column per table), **Data Mismatches** (one row per mismatched column per changed row, from `sample_changed_detail` — only populated in `FULL` mode with a real key configured, never for the row-number fallback since there's no safe way to re-query by a synthetic row number), **Row Hash Mismatches** (one row per `RowHashMismatch` — Row #/Source Schema/Source Table/Primary Key/Source Hash/Target Hash/Mismatch Status, where Row # is a sequential number assigned after sorting — populated whenever a key is configured *or* the row-number fallback ran), and **Suggestions** (`_build_suggestion_rows` — every `FAIL`/`ERROR` table gets at least one plain-English sentence, covering every category that can independently fail a table: schema/constraint issues (missing/extra column, column order, data type, nullable), per-column statistics (null count, distinct count, min/max), row count, and row-level data — the last of these points at the Data Mismatches/Row Hash Mismatches sheets for full detail rather than duplicating it; an "Unclassified" fallback row fires if a table is FAIL/ERROR but none of the specific checks explain why, so a failed table is never left unexplained; if a table failed purely on schema/constraint or statistics grounds while its row data actually matched, an extra "Summary" row calls that out explicitly). All sheets get frozen header rows, autofit column widths, `auto_filter`, and PASS=green/FAIL=red/ERROR=orange/SKIPPED=gray fills via `STATUS_FILLS`/`STATUS_FONTS` (the Row Hash Mismatches sheet maps its non-`ValidationStatus` string statuses onto the same fills via `_ROW_HASH_STATUS_FILL_MAP`). "Schema Match" reuses `columns_status` (column-name match, not a separate concept). `POST /validate-catalogs/report?format=csv|excel` (default csv) and the CLI's `--csv`/`--excel` flags (either or both) select the format.

3. **Azure Blob CSV vs. single Databricks table** (`AzureCsvValidator` in `azure_row_validator.py`, CLI `validate-csv` only — no HTTP endpoint yet) — same validation stages as `CatalogValidator` (column names/order, data types, row count, null/distinct/min-max, row-hash comparison, row-level data-mismatch detail) but for exactly one CSV file against one table, since a CSV has no schemas/multiple-tables structure. Returns the *same* `CatalogValidationResponse` shape as `CatalogValidator` (one `SchemaValidationResult` wrapping one `TableValidationResult`), so `report_generator.py` needed zero changes - it just sees "one schema, one table."

   - Despite the name, `AzureConnector.read_csv` auto-detects the blob's actual format from its file extension and dispatches to `pd.read_csv`/`pd.read_excel`/`pd.read_parquet` accordingly (`.csv`/`.txt` -> CSV, `.xlsx`/`.xls` -> Excel, `.parquet` -> Parquet) - the method name is kept only for backward compatibility with existing callers. The source blob's format is completely independent of the target Databricks table's own storage format, which is always queried via SQL regardless of what format Databricks stores it in internally - so e.g. a Parquet blob compared against a Delta-backed Databricks table already works with no special-casing needed.

   - The Databricks side of row-hash comparison is unchanged (`DatabricksConnector.get_row_hashes`, pushed-down SQL). The CSV side has no SQL engine behind it, so `AzureCsvValidator._hash_csv_rows` hashes rows in Python via `hashlib.sha256` - verified empirically to produce byte-identical hex digests to Databricks' `sha2(x, 256)` for the same input string, so the two sides' hashes are directly comparable.
   - The hard part: each CSV cell must be formatted to match Databricks' `CAST(col AS STRING)` output for that column's **target** type before hashing (e.g. a `double` column always gets a trailing `.0` even for whole numbers, but `bigint` never does) - `_format_value_for_hash` does this using the *target table's real Databricks schema* as ground truth (fetched via `get_table_schema`), not the CSV's own pandas-inferred dtypes, since those two can disagree (this is exactly the double-vs-string class of bug found and fixed in `databricks_connector.py`'s `values_differ` earlier).
   - `databricks_connector.py`'s tolerant value-comparison logic (numeric types incl. `Decimal`/numpy scalars, `date` vs `datetime`, but NOT numeric-vs-string) was extracted from a private closure into a shared module-level `values_differ()` function specifically so `azure_row_validator.py` and `azure_sql_validator.py` could reuse it for row-hash-mismatch column-level diffing and min/max comparison without duplicating the logic.
   - `CsvTableValidationRequest.primary_key` (`models.py`) is optional (`default_factory=list`) — if omitted, `AzureCsvValidator._hash_csv_rows_by_row_number` sorts the CSV DataFrame by every value column (matching the `ORDER BY` used on the Databricks side) before assigning sequential row numbers, so the same fallback semantics as `CatalogValidator` apply.

4. **Azure SQL Database vs. Databricks catalog** (`AzureSqlValidator` in `azure_sql_validator.py`, CLI `validate-sql` only — no HTTP endpoint yet) — multi-table version of the CSV path: every table in the Azure SQL database (optionally restricted via `request.schemas`/`tables`) is matched **by name** against a like-named Databricks table, mirroring `CatalogValidator`'s schema/table matching, and every matched pair goes through the same per-table pipeline. Returns the same `CatalogValidationResponse` shape.

   - `AzureSqlValidationRequest.schema_map` (`models.py`) + CLI `--schema-map 'dbo=target_schema'` handles the common case where Azure SQL's default `dbo` schema doesn't share a name with the target Databricks schema — without a mapping, schema matching is by identical name only and silently finds zero common tables.
   - Both `_compare_schemas` and `_compare_tables` return **`(source_name, target_name)` pairs**, not single names — schema/table names are matched case-insensitively but each side's own casing must be preserved and used for that side's own subsequent lookups, since Databricks' `information_schema` table-name match (and Azure SQL's) is case-sensitive. Passing the source's casing to both sides' lookups was a real bug found and fixed here (a table existed as `file_example_XLSX_100` on one side and `file_example_xlsx_100` on the other; using one casing for both lookups silently produced zero common columns on the wrong-cased side).
   - Row-hash comparison is pushed down on **both** sides here (unlike the CSV path): `AzureSqlConnector.get_row_hashes` builds `HASHBYTES('SHA2_256', ...)` SQL, formatting each column via `_hash_string_expr` to match Databricks' `sha2()`/`CAST(... AS STRING)` conventions as closely as T-SQL allows. Verified empirically against real data (mandatory before trusting output — SQL Server and Databricks disagree on default string formatting in ways that silently corrupt every hash if unaccounted for):
     - **String columns must cast to `VARCHAR(MAX)`, not `NVARCHAR(MAX)`.** `HASHBYTES` hashes raw bytes; `NVARCHAR` is UTF-16 (2 bytes/char) while Databricks' `CAST(col AS STRING)` is UTF-8 (1 byte/char for ASCII) - identical text hashed completely differently until this was caught by comparing `DATALENGTH()` of the two forms (98 bytes vs 49 bytes for the same string). This makes the connector ASCII-only for hash-matching purposes: genuine non-ASCII text (accents, non-Latin scripts) will not hash-match Databricks' UTF-8 form and would need re-verification.
     - **`decimal`/`numeric`/`money` source columns need the synthetic `"decimal_as_integer"` type override** (`AzureSqlValidator._effective_source_types`) whenever the *target*'s real Databricks type is a plain integer (`bigint`/`int`/`smallint`/`tinyint`) — otherwise Azure SQL's fixed-scale decimal formatting (`'45000.00'`) never matches Databricks' integer string form (`'45000'`) even when the numeric value is identical, and every row appears changed.
     - `float`/`real` are formatted via `STR(x, 30, 10)` + trailing-zero trimming (keeping a `.0` minimum) to reproduce Databricks' always-decimal `double` string form, since SQL Server's default float-to-string can use scientific notation.
   - `values_differ()` needed a fix for this path too: comparing a Python `Decimal` (from `pyodbc`) against a `numpy.int64` (from a Databricks/pandas result) raised `TypeError` rather than returning `False`, because `Decimal.__eq__` doesn't recognize numpy scalar types. Fixed by widening `_NUMERIC_TYPES` from a tuple of concrete types to `numbers.Number`, which covers `int`/`float`/`Decimal` and every numpy numeric scalar in one `isinstance` check.

### Connectors (`azure_connector.py`, `databricks_connector.py`, `azure_sql_connector.py`)

- `AzureConnector` — reads CSV blobs from Azure Storage into pandas; used by the legacy `/compare` path and by `AzureCsvValidator`.
- `DatabricksConnector` — SQL Warehouse connector (`databricks-sql-connector`), lazily connects on first use, all identifiers are backtick-quoted via `_quote_ident`/`_qualify` to build safe fully-qualified names. Exposes both low-level metadata methods (`get_schemas`, `get_tables`, `get_table_schema`, `get_row_count`, `get_column_statistics`), the push-down `key_based_row_diff` used for HASH/FULL mode, `get_row_hashes` (single per-side `sha2`/`concat_ws` query) for the always-on row-hash comparison stage, and `get_row_hashes_by_row_number` (same hashing, keyed by a synthetic `ROW_NUMBER()` instead) for the no-primary-key fallback. Also exports the module-level `values_differ()` helper (tolerant cross-type-family value comparison, including numpy scalar types) used by its own `_changed_row_detail`, `azure_row_validator.py`, and `azure_sql_validator.py`.
- `AzureSqlConnector` — pyodbc/`ODBC Driver 17 for SQL Server` connector for Azure SQL Database, mirrors `DatabricksConnector`'s method names/shapes (`get_schemas`, `get_tables`, `get_table_schema`, `get_row_count`, `get_column_statistics`, `get_row_hashes`, `get_row_hashes_by_row_number`) so `AzureSqlValidator` can treat both sides symmetrically. Bracket-quotes identifiers (`[schema].[table]`, escaping embedded `]`) instead of Databricks' backticks. `_hash_string_expr` is the per-type SQL-formatting logic described above — see it before touching row-hash formatting for this path, since the formatting choices there are load-bearing, not stylistic.

### Known repo quirks

- `comparison-service/CatalogValidator.py` is **not** the catalog validator — despite its name it contains an unused, unwired `AzureDataLakeConnector` (ADLS Gen2) class. Nothing imports it. The real `CatalogValidator` class lives in `comparison_engine.py`.
- `comparison-service/test_api.py` is the pytest suite for `CatalogValidator` (all Databricks calls mocked via `unittest.mock.MagicMock`, no live Databricks needed) — despite the name, it does not test `app.py`'s HTTP layer directly.
